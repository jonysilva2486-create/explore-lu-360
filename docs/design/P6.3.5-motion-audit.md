# P6.3.5 — Motion Audit

**Status:** APPROVED / RECONCILED
**Phase:** Design System Foundations Completion
**Decision:** Motion language approved and correctly positioned as P6.3.5. The previous P6.3.4 file was a numbering error and is being removed after this corrected record is created.

## Core principle

> **Motion should explain, connect, orient and provide feedback — never entertain.**

Motion is used only when it improves understanding, continuity, orientation or interaction feedback.

## Refined enter / exit rule

> **Elements entering or leaving may animate only when the movement communicates hierarchy, continuity, spatial relationship or interaction state.**

Examples where motion is justified include Map → Place, Place → 360°, bottom-sheet expansion and Save → Saved state transitions.

Motion should normally be avoided for decorative entrance animations, every-card/list-item animation and repeated movement that increases perceived waiting time.

## Motion model

Primary functions:

1. **Orient** — understand where the user is and where they are going.
2. **Connect** — show continuity between related states or experiences.
3. **Feedback** — confirm an interaction or state change.

Guideline timing:

- Fast: approximately 120–160 ms
- Standard: approximately 200–280 ms
- Emphasis: approximately 350–450 ms

These are guidelines, not frozen tokens.

Easing categories:

- Standard
- Entrance
- Exit
- Spatial

## Spatial motion

Map → Place and Place → 360° transitions may use spatial continuity when it improves orientation. 360° motion must respect user control; automatic camera movement, unnecessary rotation and intrusive hotspot animation should be avoided.

## Bottom sheets and micro-interactions

Bottom sheets may communicate **Closed → Peek → Expanded → Collapsed** through restrained motion.

Micro-interactions such as **Save → Saving → Saved** should confirm state without becoming celebratory animation.

## Loading and system states

Loading motion must remain calm and must not replace clear system-state communication. Motion must not turn errors, offline states, permission states or unavailable content into theatrical animations.

## Reduced Motion

When reduced-motion preferences are active:

- non-essential animation is reduced or removed;
- spatial transitions may be simplified;
- functional feedback remains available;
- information never depends solely on movement.

## Performance

> **Responsiveness > animation.**

Motion must never make the application feel slower, particularly around maps, imagery, Street View, 360° content and mobile interactions.

## Architecture

**Motion Tokens → Motion Patterns → Components**

This prevents unrelated animation behaviour from being invented independently by components or developers.

# P6.3.4 — Light / Dark Behaviour

**Status:** APPROVED BY AUDIT
**Decision:** Light and Dark are two expressions of the same Explore Luxembourg 360 design language, not two separate visual identities.

## Core principles

> **One system, two visual environments.**

> **Light and Dark are two expressions of the same Explore Luxembourg 360 design language, not two separate visual identities.**

> **Theme adaptation changes visual conditions, never the underlying information architecture or interaction model.**

## Approved behaviour

### Light

The primary bright editorial environment, optimised for daylight exploration, reading, photography and maps.

### Dark

A lower-luminance, immersive environment suitable for low-light use, photography, maps and 360° experiences.

Dark mode must not be implemented as a simple colour inversion.

## Surface hierarchy

Both themes use the same structural hierarchy:

**Background → Surface → Elevated Surface → Overlay**

Dark surfaces must use differentiated tonal values rather than relying on pure black everywhere.

### Dark surface refinement — APPROVED

The project preference is for a **soft / near-black dark foundation rather than a deep absolute black**. Exact token values will be defined in the implementation token layer and validated for contrast.

The implementation must preserve visible separation between:

- Dark Background
- Dark Surface
- Dark Elevated Surface
- Dark Overlay

Pure `#000000` should not be used as the default global Dark Mode background merely for convenience.

## Controls

The same controls and interaction model operate in both themes:

- primary buttons;
- secondary buttons;
- icon buttons;
- toggles;
- segmented controls;
- sliders;
- navigation controls.

Theme changes visual tokens, not component behaviour.

## Maps

Light and Dark maps require appropriate cartographic representations. Dark mode must not be implemented as a simple dark filter over a light map.

Implementation validation must cover labels, POIs, routes, selected states, controls, contrast and zoom levels.

## Photography

Photography remains faithful to the source image. Dark Mode changes the surrounding surface, controls and context rather than artificially darkening the photograph.

## 360° experiences

The same principle applies to 360° experiences. Dark Mode may create a more immersive environment while preserving the original visual content. Controls should remain discreet, discoverable and accessible.

## System states

P6.3.3 states must work consistently in both themes:

- Loading
- Empty
- Error
- Offline
- Unavailable
- Permission

Semantic meaning and interaction remain unchanged; surface, text, icon and contrast tokens adapt to the theme.

## Typography

The typographic hierarchy remains the same across themes. Typography is not duplicated into separate systems; text colour tokens adapt to the active surface.

Typography remains part of the broader P6.1 foundation and its refinement, not a new P6.3 subsystem.

## Navigation

Navigation keeps the same position, order, labels, icons and interaction model in Light and Dark.

## Theme preference

The initial default is:

**System** — follow the operating system/browser preference.

Users may explicitly choose:

- System
- Light
- Dark

A manual choice must persist until changed by the user.

The user is not required to select a theme during onboarding.

## Motion

Theme transitions may use a short, subtle transition. The behaviour must follow P6.3.5 and respect Reduced Motion requirements from P6.3.6.

## Accessibility

Both themes must maintain readable text, visible focus, recognisable disabled states, sufficient contrast and non-colour-only communication where required.

WCAG 2.2 AA remains the product accessibility target. Visual approval does not constitute a declaration of technical compliance.

## Disabled states

Disabled controls must remain recognisable as controls. Reduced emphasis must not become invisibility, particularly in Dark Mode.

## Design-token direction

Shared tokens remain shared across themes for:

- spacing;
- radius;
- typography scale;
- icon size;
- layout;
- grid.

Theme-specific tokens primarily adapt:

- surfaces;
- text colours;
- control colours;
- borders;
- elevation;
- contrast.

## Initial content compatibility

The theme system supports the actual initial production strategy:

- routes;
- Google Street View;
- exterior photography;
- viewpoints;
- exterior monument documentation;
- place information.

It is also prepared for future richer content such as own 360° capture, authorised interiors and deeper editorial experiences.

## Audit result

**P6.3.4 — Light / Dark Behaviour: APPROVED BY AUDIT.**

The visual demonstration was approved and the audit found no structural design objection.

The only implementation-level work remaining is to define and test exact design-token values, especially the soft/near-black Dark surfaces, and validate map, contrast, focus and device behaviour during implementation.

## Final P6.2 principles

### 1. Continuous exploration

The product should feel like a continuous exploration flow rather than a collection of administrative pages.

**Explore → Discover → Explore → Continue**

### 2. Map-first exploration

The map is one of the places where exploration happens. It connects geographic context to Places, Routes and 360° experiences.

### 3. Place as the core content experience

Places provide the contextual bridge between geographic discovery, stories, media, routes and immersive experiences.

### 4. Search as exploration

Search is a layer of exploration, not a destination. Users can search when they know what they want and discover when they do not.

### 5. 360° as experience

360° is not a feature. It is an experience layer. The platform is designed for the full experience while initial content is produced incrementally and realistically.

### 6. Account-based memory

> **Accountless exploration. Account-based memory.**

Exploring, searching, viewing and sharing do not require an account. Save, Collections, Saved Routes, My Explore and synchronisation require an account.

## Initial content reality

The initial Explore Luxembourg 360 content strategy remains intentionally realistic:

- routes, primarily using Google Street View where appropriate;
- own photography of viewpoints, landscapes and selected places;
- exterior documentation of monuments and places of interest.

The architecture is prepared for future expansion into proprietary 360° capture, interior monument mapping and institutional/partner content.

## Géoportail readiness

The map architecture must remain open to future Géoportail integration/collaboration as an important mapping and public-sector layer. No single map provider should become an architectural lock-in.

## PDR-005 reconciliation

PDR-005 previously described local anonymous Save state. That wording has been corrected. The approved rule is now:

- exploration without account;
- Save requires account;
- Collections require account;
- My Explore requires account;
- cloud synchronisation requires account;
- sharing does not require account.

## PDR-006 relationship

PDR-006 defines the broader Visual Language / Design System foundations. P6.2 defines the approved component language being developed within that visual system. P6.2 is therefore subordinate to PDR-006 and must not introduce visual rules that conflict with the approved visual language.

## GitHub reconciliation result

At the beginning of this audit, the repository was behind the approved project decisions: P6.2.2, P6.2.4, P6.2.5 and P6.2.6 had been approved in the working process but were not yet documented in GitHub. This reconciliation adds those documents and updates PDR-005 so that the account/save model is consistent.

## Gate before continuing

No new P6.2 component should be invented or advanced solely from conversational momentum. Before continuing, the next component must be identified against the approved project matrix and the repository state.

# P6.3.6 — Accessibility Audit

**Status:** APPROVED / RECONCILED
**Phase:** Design System Foundations Completion
**Decision:** Accessibility is an integral part of the Explore Luxembourg 360 experience. WCAG 2.2 AA is the product target; actual conformance must be validated through implementation and real testing. The numbering is reconciled to the original P6.3 plan.

## Audit purpose

Validate the approved P6.3.6 Accessibility direction against the P6.1 visual language, P6.3.1 iconography, P6.3.2 controls, System States, P6.3.5 Motion, multilingual requirements and the project's real content-production strategy.

## Approved principle

> Accessibility does not create a separate version of Explore Luxembourg 360. It is part of the same experience, designed so that different users can reach the same meaningful information and goals through appropriate paths.

Secondary design principle:

> Accessible by design. Beautiful by default.

## Accessibility target

**WCAG 2.2 AA** is the reference target for the product.

This is a target and design requirement, not a claim of current compliance. Compliance can only be declared after implementation and validation.

## Contrast

Design must meet the applicable contrast requirements:

- Normal text: minimum 4.5:1
- Large text: minimum 3:1
- UI components and graphical objects: adequate contrast where contrast is necessary to identify information or state

Premium visual styling must never override legibility.

## Colour independence

Colour must not be the sole carrier of meaning. States should use an appropriate combination of text, iconography, pattern, position, shape or other non-colour cues.

## Touch targets

The design baseline is **44 × 44 px** minimum interactive area on touch interfaces. Visual icons may be smaller while retaining a larger invisible hit area.

Final implementation must validate spacing between targets, device density, browser behaviour and overlapping interactive areas.

## Keyboard interaction and focus

Applicable interactive functionality must be usable by keyboard, with logical focus order, no keyboard traps and clearly visible focus states.

Focus must not depend only on colour and must integrate with the visual identity without becoming invisible or ambiguous.

## Semantic structure and screen readers

Use semantic HTML and appropriate accessibility semantics for buttons, links, headings, landmarks, forms, dialogs and images.

Do not use generic containers as substitutes for native semantic interactive elements when a native element is available.

## Images and alternative text

Informative photography must receive meaningful alternative text when it conveys information necessary to understand the experience. Purely decorative imagery may use an empty alternative where appropriate.

Descriptions should be concise and purposeful rather than automatically generating long descriptions for every photograph.

## 360° experiences

> The 360° experience enhances access to a place; it must not be the only way to understand it.

Where necessary, 360° experiences should be accompanied by standard photography, textual description, map information, place information and named points of interest.

## Google Street View experiences

The initial product may rely heavily on Google Street View, but essential information must not depend exclusively on the Street View interface. Where applicable, users should have place information, description, map and alternative imagery.

## Motion and reduced motion

P6.3.6 inherits the approved **P6.3.5 Motion** principles. The product should respect user preferences such as `prefers-reduced-motion` by reducing or removing non-essential movement while preserving functional feedback, state changes and orientation.

**Reduced motion must not mean reduced functionality.**

## Text resizing and zoom

The layout must remain usable when text is enlarged and when users zoom the interface. Content must not be arbitrarily clipped, overlapped or made inaccessible by scaling.

## Multilingual accessibility

The six initial product languages are:

- French — Français
- German — Deutsch
- English
- Dutch — Nederlands
- Portuguese — Português
- Luxembourgish — Lëtzebuergesch

Accessibility and typography must work across all six languages, including expansion in text length, special characters, labels and screen-reader output.

## Cognitive accessibility

The interface should minimise unnecessary cognitive load through few purposeful choices, predictable navigation, clear language, consistent interaction patterns, limited decorative animation, understandable error messages and strong visual hierarchy.

## Maps

Essential spatial information must not exist only as a visual map representation. Where applicable, textual or structured information should accompany the map, for example:

**12.4 km · Moderate · 3h 20**

The final accessibility behaviour of interactive maps will be validated during implementation because it depends partly on the selected mapping technology and its capabilities.

## Forms and errors

Forms must provide clear labels, appropriate focus, understandable validation, accessible error identification and actionable recovery guidance.

## Testing strategy

Accessibility validation must occur at four levels:

### Automated
Validate applicable semantics, contrast, attributes and other machine-testable requirements.

### Keyboard
Use the product without a mouse and validate focus order, focus visibility and interaction completion.

### Screen reader
Validate meaningful navigation, labels, headings, controls, images and dynamic states with screen-reader technology.

### Real interaction
Test text resizing, zoom, reduced motion, different devices, different languages and real user scenarios.

Real-user testing is essential because automated checks cannot fully measure usability.

## Reconciliation note

P6.3.6 remains the final accessibility foundation in the original approved sequence. References have been corrected so Motion is P6.3.5 and System States is P6.3.3. The existence of open reconciliation work in those earlier points does not invalidate the approved accessibility principles, but P6.3 itself cannot be declared closed until the complete sequence is reconciled.

## Audit conclusion

**P6.3.6 — Accessibility is APPROVED BY AUDIT.**

The design decision remains approved. Final technical compliance remains subject to implementation and testing.

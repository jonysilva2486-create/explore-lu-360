# P6.3.6 — Accessibility Audit

**Status:** APPROVED
**Phase:** Design System Foundations Completion
**Decision:** Accessibility is an integral part of the Explore Luxembourg 360 experience. WCAG 2.2 AA is the product target; actual conformance must be validated through implementation and real testing.

## Audit purpose

Validate the approved P6.3.6 direction against the P6.1 visual language, P6.3.1 iconography, P6.3.2 controls, P6.3.3 system states, P6.3.4 motion, P6.3.5 typography, multilingual requirements and the project's real content-production strategy.

## Approved principle

> Accessibility does not create a separate version of Explore Luxembourg 360. It is part of the same experience, designed so that different users can reach the same meaningful information and goals through appropriate paths.

Secondary design principle:

> Accessible by design. Beautiful by default.

## Accessibility target

**WCAG 2.2 AA** is the reference target for the product.

This is a target and design requirement, not a claim of current compliance. Compliance can only be declared after implementation and validation.

## Contrast

Design must meet the applicable contrast requirements:

- Normal text: minimum 4.5:1
- Large text: minimum 3:1
- UI components and graphical objects: adequate contrast where contrast is necessary to identify information or state

Premium visual styling must never override legibility.

## Colour independence

Colour must not be the sole carrier of meaning. States should use an appropriate combination of text, iconography, pattern, position, shape or other non-colour cues.

Example:

**Colour only:** not sufficient.

**Colour + icon + label:** preferred.

## Touch targets

The design baseline is **44 × 44 px** minimum interactive area on touch interfaces. Visual icons may be smaller while retaining a larger invisible hit area.

The final implementation must additionally validate spacing between targets, device density, browser behaviour and overlapping interactive areas.

## Keyboard interaction

All applicable interactive functionality must be usable by keyboard, including:

- navigation;
- buttons and links;
- search;
- filters;
- collections;
- dialogs and bottom sheets;
- galleries;
- applicable map controls.

Focus order must be logical and keyboard traps must be avoided.

## Focus states

Every keyboard-focusable control must have a clearly visible focus state. Focus must not depend only on colour and must integrate with the visual identity without becoming invisible or ambiguous.

## Semantic structure and screen readers

Use semantic HTML and appropriate accessibility semantics:

- real buttons for button behaviour;
- real links for navigation;
- semantic headings;
- meaningful landmarks;
- accessible forms;
- appropriate dialog semantics;
- appropriate image semantics.

Do not use generic containers as substitutes for semantic interactive elements when a native element is available.

## Images and alternative text

Informative photography must receive meaningful alternative text when it conveys information necessary to understand the experience.

Purely decorative imagery may use an empty alternative where appropriate.

Descriptions should be concise and purposeful rather than automatically generating long descriptions for every photograph.

## 360° experiences

> The 360° experience enhances access to a place; it must not be the only way to understand it.

A 360° experience should be accompanied, where necessary, by meaningful alternatives such as:

- standard photography;
- textual description;
- map information;
- place information;
- named points of interest.

## Google Street View experiences

The initial product may rely heavily on Google Street View for route and place exploration, but essential information must not depend exclusively on the Street View interface.

Where applicable, users should have access to:

- place information;
- description;
- map;
- alternative imagery.

## Motion and reduced motion

P6.3.6 inherits the P6.3.4 motion principles. The product should respect user preferences such as `prefers-reduced-motion` by reducing or removing non-essential movement while preserving functional feedback, state changes and orientation.

**Reduced motion must not mean reduced functionality.**

## Text resizing and zoom

The layout must remain usable when text is enlarged and when users zoom the interface. Content must not be arbitrarily clipped, overlapped or made inaccessible by scaling.

Responsive typography is therefore structural, not merely a matter of shrinking desktop sizes.

## Multilingual accessibility

The six initial product languages are:

- French — Français
- German — Deutsch
- English
- Dutch — Nederlands
- Portuguese — Português
- Luxembourgish — Lëtzebuergesch

Accessibility and typography must work across all six languages, including expansion in text length, special characters, labels and screen-reader output.

Language rollout terminology remains:

**Initial Full Localisation**
- French
- German
- English
- Dutch

**Progressive Full Localisation**
- Portuguese
- Luxembourgish

**Future Expansion**
- Italian
- Spanish
- other languages justified by audience and production capacity

These categories describe production rollout, not language or cultural importance.

## Cognitive accessibility

The interface should minimise unnecessary cognitive load through:

- few, purposeful choices;
- predictable navigation;
- clear language;
- consistent interaction patterns;
- limited decorative animation;
- understandable error messages;
- strong visual hierarchy.

The existing principle of **few buttons + strong visual hierarchy + predictable interaction** supports this goal.

## Maps

Essential spatial information must not exist only as a visual map representation.

Where applicable, textual or structured information should accompany the map, for example:

**12.4 km · Moderate · 3h 20**

The final accessibility behaviour of interactive maps will be validated during implementation because it depends partly on the selected mapping technology and its capabilities.

## Forms and errors

Forms must provide:

- clear labels;
- appropriate focus;
- understandable validation;
- accessible error identification;
- actionable recovery guidance.

Error messages should explain the problem and help the user recover rather than exposing technical language.

Example:

**We couldn't find that location. Try another place name.**

## Content strategy and accessibility

Accessibility must work with the project's actual launch content:

- exterior photography;
- Google Street View;
- routes;
- viewpoints;
- monuments and places;
- concise contextual information.

Future content such as own 360° capture, authorised interiors and deeper historical/editorial material should enrich the same accessible structure rather than require a separate design system.

## Testing strategy

Accessibility validation must occur at four levels:

### Automated

Validate applicable semantics, contrast, attributes and other machine-testable requirements.

### Keyboard

Use the product without a mouse and validate focus order, focus visibility and interaction completion.

### Screen reader

Validate meaningful navigation, labels, headings, controls, images and dynamic states with screen-reader technology.

### Real interaction

Test text resizing, zoom, reduced motion, different devices, different languages and real user scenarios.

Real-user testing is essential because automated checks cannot fully measure usability.

## Device capability and accessibility

Technical limitations of a particular device or browser must not automatically be interpreted as an accessibility failure. When a preferred interaction is unavailable, the product should provide another meaningful route to the same essential information or goal whenever technically feasible.

## Audit conclusion

**P6.3.6 — Accessibility is APPROVED BY AUDIT.**

No structural contradiction was found. The remaining yellow items are implementation validations, not design objections.

- P6.3.2 — Buttons & Controls

# P6.3.3 — System States Audit

**Status:** APPROVED
**Phase:** Design System Foundations
**Decision:** System states are approved as a coherent, calm and resilient interaction system. The system distinguishes loading, empty, error, offline, unavailable and permission states and provides the clearest available next step.

## Approved principle

> A system state should explain what is happening without making the interface feel broken.

Supporting rule:

> Every system state must communicate status, preserve trust, and provide the clearest available next step.

## State model

| State | Meaning | Typical response |
|---|---|---|
| Loading | The system is working | Keep the user informed; use skeletons or progress when meaningful |
| Empty | The feature has no content | Explain the value and provide a relevant next action |
| Error | Something failed | Explain what happened and provide recovery |
| Offline | Connectivity is unavailable | Explain the limitation and show what remains available |
| Unavailable | Specific content or experience cannot currently be used | Explain the limitation and provide a meaningful alternative |
| Permission | User authorisation is required | Explain the benefit and offer a clear choice |

## Loading

Use skeletons for structural loading and progress indicators when an operation has meaningful duration. Avoid loading indicators for operations so fast that the indicator itself would create visual noise.

Loading must preserve the underlying hierarchy and remain consistent with typography, spacing, iconography, dark/light behaviour and motion rules.

## Empty

Meaningful empty states should answer:

1. What is happening?
2. Why does this feature matter?
3. What can the user do next?

Example:

**Your collection is empty**

*Save places you love and find them here later.*

**Explore places**

Empty states should not use generic technical wording such as `No data` when a more useful explanation is possible.

## Error

Errors should be specific whenever the system has enough information to explain the failure.

Preferred pattern:

**What happened → what the user can do.**

Example:

**We couldn't load this place.**

*Please check your connection and try again.*

**Try again**

**Back to Explore**

`Something went wrong` remains a fallback only when the system cannot provide a more specific explanation.

## Offline

Offline is not treated as a generic error. The product may be used in forests, trails, rural areas and other locations where connectivity can vary.

The system should distinguish:

- no network connection;
- content unavailable because it was not previously available offline;
- content that remains accessible while offline.

The visual demonstration includes **Downloaded content** as a future capability, not a launch commitment.

Future offline/download functionality must integrate with the existing Save + Collections architecture rather than creating a separate mental model.

## Unavailable

Unavailable content should not unnecessarily block the wider place experience.

Examples:

- 360° unavailable → offer photos and place information;
- Street View unavailable → offer map and place information;
- a future experience temporarily unavailable → retain the accessible information that remains available.

Core rule:

> A failure of one layer must not unnecessarily become a failure of the entire place experience.

## Permission

When practical, explain the benefit before requesting permission.

Example:

**Location helps us show places near you.**

**Allow location**

**Not now**

Users must retain a meaningful way to continue when permission is not granted, unless the requested permission is intrinsically required for the specific action.

## Visual consistency

All system states belong to the same Explore Luxembourg 360 visual language:

- same typography system;
- same iconography language;
- same spacing principles;
- same surface and colour language;
- same editorial tone;
- same accessibility expectations.

A system error must not visually turn the product into a generic technical interface.

## Action hierarchy

Primary actions should be limited to the most useful recovery or continuation path, for example:

- Try again
- Explore places
- View photos
- View on map

Secondary actions may include:

- Back to Explore
- Back to place information
- Not now

System states should not present multiple competing actions with equal visual weight.

## Scope: global vs local

The system must distinguish global conditions from local conditions.

**Global:**

> You're offline.

**Local:**

> Street View is unavailable for this location.

A local failure should not unnecessarily place the entire application into a global error state.

## Duration: temporary vs persistent

System states should distinguish between temporary and persistent conditions.

**Typically temporary:**
- Loading
- Recoverable error
- Permission request

**Potentially persistent:**
- Empty
- Unavailable
- Offline

This distinction should influence persistence, dismissal, priority and where the message appears.

## Accessibility

System states must comply with the P6.3.6 accessibility principles:

- do not communicate state through colour alone;
- provide meaningful text;
- announce relevant dynamic states to screen readers;
- preserve keyboard access and visible focus;
- support reduced motion;
- provide understandable recovery paths.

## Multilingual readiness

All system-state copy must support the six initial product languages:

- Français
- Deutsch
- English
- Nederlands
- Português
- Lëtzebuergesch

Text must wrap naturally and remain usable across language expansion.

## Content scalability

The state system supports the current launch content model:

- exterior photography;
- routes;
- viewpoints;
- monuments and places;
- Google Street View.

It also supports future layers such as own 360° capture, authorised interior experiences and deeper editorial content without requiring a new state architecture.

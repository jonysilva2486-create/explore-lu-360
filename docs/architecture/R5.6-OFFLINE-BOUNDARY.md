# Explore Luxembourg 360 — R5.6 Offline Boundary

**Status:** APPROVED — VISUAL DEMONSTRATION APPROVED — READY FOR AUDIT  
**Version:** v1.0 — August 2026

## Purpose

Define what the Explore Luxembourg 360 MVP can do without connectivity, what requires connectivity, how intentionally downloaded experiences are stored locally, and how offline changes synchronize when connectivity returns.

## Core principle

**The MVP provides offline capability for intentionally downloaded experiences and their essential geographic, editorial and media content. It does not attempt to make the entire platform fully offline.**

Online-only functionality must fail gracefully and clearly indicate when connectivity is required.

## 1. Connection States

### Online

Full connectivity and full platform functionality.

### Degraded

Weak or intermittent connectivity. The application should continue using locally available data where possible and avoid repeatedly blocking the user while waiting for network responses.

### Offline

No Internet connectivity. The application remains functional within the limits of data previously downloaded or locally available.

## 2. Offline MVP Capabilities

The following may be available offline when included in an intentionally downloaded experience:
- experience editorial content;
- route and waypoints;
- essential POIs;
- offline map data for the selected area;
- GPS/GNSS position;
- optimized photographs;
- optimized 360 panoramas;
- Stories/editorial content;
- already synchronized favorites/saved items;
- basic progress tracking;
- local notes where implemented.

GPS/GNSS does not require an Internet data connection, although device hardware and operating-system conditions still apply.

## 3. Offline Package

An offline package is explicitly user-controlled and scoped to an experience/area.

Conceptual contents:

```text
Experience metadata
+ Route / GPX data
+ Map data for selected area
+ Essential POIs
+ Optimized photos
+ Optimized 360
+ Stories / editorial
+ Manifest / version / checksums
```

The package must not include the full media library or unnecessary private data.

The user must see package size/storage requirements before downloading.

## 4. Offline Maps

The MVP does not attempt to make the entire country available offline by default.

Offline map coverage is scoped to the selected experience and a reasonable surrounding area required for that experience.

The exact map technology and licensing constraints are defined by the approved mapping architecture and provider decisions in the relevant R4 documentation.

## 5. GPS / Positioning

GPS/GNSS positioning may continue without Internet connectivity.

The application may display the user's position against locally stored map and route data.

The application must not imply that live online services are available when they are not.

## 6. Offline Navigation Boundary

### MVP supported
- display downloaded route;
- display downloaded map area;
- display current GPS position;
- show waypoints and essential POIs;
- show basic progress.

### MVP not promised
- dynamic online routing;
- live traffic or live conditions;
- server-dependent route recalculation;
- real-time updates;
- online search across the platform.

## 7. Offline 360 / Media

Offline 360 uses optimized derivatives rather than production masters.

```text
360 Master
   ↓
Optimized offline derivative
   ↓
Device
```

The same principle applies to photographs and future video derivatives.

Future 3D capture remains a supported architectural direction but is not an MVP offline requirement.

## 8. Offline Data Changes

Offline changes are local until successfully synchronized.

```text
Offline action
    ↓
Local state
    ↓
Pending sync
    ↓
Connectivity returns
    ↓
Sync
    ↓
Server confirmation
    ↓
Synced
```

The MVP should keep offline mutations deliberately limited to simple, low-conflict actions such as local saves/favorites, where implemented.

Complex authoring, administrative changes and uploads remain online-only.

## 9. Conflict Handling

Conflicts must never be silently overwritten.

If an offline change conflicts with a server-side change, the application must preserve the local state and/or pending operation and apply an explicit conflict-resolution policy appropriate to that data type.

## 10. Authentication Boundary

First-time account creation, initial login and account recovery require connectivity.

An already authenticated user may continue to access eligible previously downloaded content subject to the application's session/security policy.

Offline mode must not require storage of provider secrets, private API credentials or authentication secrets on the device.

## 11. Offline Security

Offline content is treated as cached application data, not as a secure vault.

The offline package must not contain:
- server secrets;
- provider credentials;
- administrative credentials;
- unnecessary personal data;
- private API keys.

Local application storage should use appropriate operating-system/application protections available to the chosen platform.

## 12. Freshness / Versioning

Every offline package must carry version/timestamp metadata sufficient to determine whether an update is available.

Example:

```text
Downloaded: 2026-09-01
Content version: v12
Last validated: 2026-09-01
```

When connectivity returns, the application should check for updates and refresh the package as appropriate.

Future incremental/delta package updates may reduce bandwidth and storage requirements.

## 13. Offline Storage Management

Users must be able to:
- see downloaded experiences;
- see storage usage/size per package;
- delete an offline package;
- manage available local storage.

Deleting an offline package must not silently delete the user's online account data, favorites or collections.

## 14. Online-only Features

The following remain online-only for MVP:
- first-time login;
- account creation;
- password/account recovery;
- global online search;
- live/dynamic information;
- dynamic online routing;
- content not previously downloaded;
- uploads to R2;
- administrative/management functions;
- moderation;
- full online synchronization;
- advanced authoring;
- full-country offline coverage;
- offline 3D authoring/advanced 3D workflows.

## 15. Architecture

```text
                    USER INTERFACE
                          │
                  EXPERIENCE ENGINE
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
       ONLINE SERVICES            LOCAL STORAGE
             │                         │
        API / R2 / Auth          Map / Data / Media
             │                         │
             └────────────┬────────────┘
                          ▼
                    SYNC MANAGER
                          │
               when connectivity exists
                          ▼
                     SERVER STATE
```

The experience layer decides whether required information can be served locally or must be requested online.

## 16. Graceful Degradation

When an online-only capability is requested without connectivity, the application must:
- avoid indefinite loading;
- clearly communicate that connectivity is required;
- preserve locally available user state;
- avoid losing offline changes;
- return to normal online behavior when connectivity resumes.

## 17. Offline Lifecycle

```text
Download
   ↓
Verify / Store
   ↓
Use offline
   ↓
Local pending changes (if supported)
   ↓
Connectivity returns
   ↓
Sync / Validate
   ↓
Confirmed state
```

## 18. MVP Boundary

The project deliberately chooses **offline-capable where it materially improves the outdoor experience**, rather than a fully offline architecture.

### In scope
- intentional offline downloads;
- selected geographic/content package;
- GPS position;
- route and essential POIs;
- optimized photos and 360;
- editorial content;
- controlled local storage;
- limited offline mutations and synchronization.

### Out of scope for MVP
- entire Luxembourg offline by default;
- complete dynamic routing engine;
- real-time data;
- offline upload pipeline;
- offline account creation;
- full offline search;
- offline 3D authoring.

## 19. Future Evolution

Potential future capabilities include:
- richer offline navigation;
- improved offline search;
- incremental package updates;
- more advanced offline synchronization;
- offline 3D viewing;
- broader geographic packages;
- more sophisticated conflict resolution.

These are evolutionary options, not MVP commitments.

## 20. Guiding Experience

```text
Prepare before you go
        ↓
Enjoy anywhere
        ↓
Sync when you return
```

The goal is not to reproduce the entire online platform without Internet access. The goal is to ensure that the outdoor experience does not unnecessarily stop when connectivity disappears.

# Explore Luxembourg 360 — R5.6 MVP Offline Boundary

**Status:** REFINED — ESSENTIAL MVP SCOPE — READY FOR FINAL AUDIT  
**Version:** v1.1 — August 2026

## Purpose

Define the minimum offline resilience required for the Explore Luxembourg 360 MVP without turning the MVP into a full offline-first application.

## Core principle

**The MVP is offline-aware, not offline-first.**

The MVP should remain usable when connectivity disappears, but it does not attempt to reproduce the entire online platform offline. More complete offline capabilities remain an explicit future evolution path.

## 1. Connection States

### Online
Full connectivity and platform functionality.

### Degraded
Weak or intermittent connectivity. The application should prefer locally available information where practical and avoid indefinite loading or repeated blocking requests.

### Offline
No Internet connectivity. The application remains usable only within the limits of information already available locally.

## 2. Essential MVP Offline Capabilities

The MVP should support only the essential resilience needed for the outdoor experience:
- continue viewing content that has already been successfully loaded and remains available locally;
- continue viewing locally available images and 360 derivatives;
- continue displaying an already available experience and its route/data where those resources are locally available;
- display GPS/GNSS position when the device provides it;
- preserve locally available user state;
- clearly indicate when a requested capability requires connectivity.

The MVP does **not** require a dedicated full offline-download/package system.

## 3. Offline Content Boundary

Content is available offline only when it has already been loaded and is still available in the application's local storage/cache.

The application must not imply that arbitrary online content is available offline.

If required content is unavailable locally, the UI must clearly indicate that connectivity is required.

## 4. Offline Maps & Routes

The MVP does not implement a dedicated downloadable offline-map system or full offline navigation engine.

If map/route resources are already locally available, the application may continue displaying them without connectivity.

GPS/GNSS positioning may continue without an Internet data connection, subject to device hardware, permissions and environmental conditions.

Dedicated offline maps, navigation and route recalculation are future capabilities.

## 5. Offline 360 / Media

The MVP may continue displaying 360 panoramas and photographs that are already locally available.

It does not require a dedicated offline 360 download system or special offline media package.

Production masters are never stored on the device merely to support offline viewing. Offline viewing uses the normal optimized application assets where available.

Future versions may introduce explicit downloadable 360/media packages.

## 6. Offline Data Changes

The MVP is primarily read-oriented while offline.

No full offline synchronization system is required.

Simple local UI state may be preserved where practical, but server-side mutations such as authoring, moderation, uploads and administrative actions remain online-only.

Future versions may introduce offline saves/favorites, pending operations and synchronization.

## 7. Authentication Boundary

First-time account creation, initial login and account recovery require connectivity.

An already authenticated user may continue to access locally available eligible content, subject to the application's normal session and security policy.

Offline mode must never bypass session expiry, revocation or other security controls.

The device must never receive provider secrets, private API credentials or authentication secrets merely to support offline operation.

## 8. Offline Security

Offline content is cached application data, not a secure vault.

The MVP must not place secrets or unnecessary private data into local storage/cache.

Protection of local data must use the security capabilities appropriate to the selected platform/browser. The architecture does not make an unconditional encryption claim for all local storage.

## 9. Graceful Degradation

When connectivity is unavailable, online-only capabilities must:
- avoid indefinite loading;
- clearly communicate that connectivity is required;
- preserve locally available state;
- avoid silently losing local user state;
- recover normally when connectivity returns.

## 10. Local Storage Architecture

"Local storage" is an architectural abstraction and does not mean the browser `localStorage` API.

The final implementation may use appropriate browser/platform mechanisms such as Service Worker caches and IndexedDB or equivalent storage, selected according to the actual application architecture and browser/platform constraints.

The MVP must not assume unlimited or permanent local storage. Storage eviction, quota and device constraints must be handled gracefully by the implementation.

## 11. Future Offline Evolution

The following are deliberately deferred and are **not MVP commitments**:
- explicit downloadable experiences;
- dedicated offline packages/manifests;
- dedicated offline maps;
- full offline navigation;
- offline search;
- offline saves/favorites with server synchronization;
- conflict resolution and idempotent sync queues;
- offline uploads;
- advanced offline 360/media packages;
- offline 3D viewing/authoring;
- full-country offline coverage.

These capabilities may be introduced incrementally based on real user needs, technical constraints and product priorities.

## 12. Future Architecture Direction

The MVP boundary must not prevent a later evolution toward:

```text
Online
   ↓
Offline-capable
   ↓
Downloaded Experiences
   ↓
Offline Maps / Navigation
   ↓
Offline Sync
   ↓
Advanced 360 / 3D Offline
```

Future offline functionality should be added as incremental capabilities rather than forcing a full offline-first rewrite unless future requirements justify it.

## 13. MVP Decision Matrix

| Capability | MVP | Future |
|---|---|---|
| Continue locally available content | 🟢 | — |
| GPS/GNSS without Internet | 🟢 | — |
| Already available route/map data | 🟢 | — |
| Graceful offline/degraded behavior | 🟢 | — |
| Explicit offline experience download | — | 🔵 |
| Dedicated offline maps | — | 🔵 |
| Offline navigation | — | 🔵 |
| Offline sync | — | 🔵 |
| Offline search | — | 🔵 |
| Offline upload | — | 🔵 |
| Advanced offline 360 | — | 🔵 |
| Offline 3D | — | 🔵 |
| Full-country offline | — | 🔵 |

## 14. Guiding Experience

```text
Use what is already available
          ↓
Stay useful when the signal disappears
          ↓
Reconnect when needed
          ↓
Future updates can add deeper offline capability
```

The goal of R5.6 is resilience, not feature completeness. The Explore Luxembourg 360 MVP should not become a second offline application before real usage demonstrates that the additional complexity is justified.

# Explore Luxembourg 360 — R5.2 CI/CD & Release Operations

**Status:** CLOSED — APPROVED — FINAL AUDIT PASS  
**Version:** v1.2 — August 2026

## Purpose

Define the smallest credible CI/CD and release process for the first vertical slice so that every production release is tested, traceable and reversible.

## Core principle

> **Every production release must be tested, traceable and reversible.**

The project must not overbuild its delivery infrastructure before product validation.

## 1. Source control

GitHub is the source of truth for application code and project configuration.

- `main` is protected.
- Direct pushes to `main` are prohibited.
- Feature/fix branches are used for changes.
- Pull Requests are the normal integration mechanism.
- Required CI checks must pass before merge.
- Important releases may be tagged/versioned.

## 2. Continuous Integration

GitHub Actions is the primary CI layer for the MVP.

Required checks:

1. ESLint
2. TypeScript type checking
3. Unit tests
4. Build verification

Recommended checks where practical:

- integration tests;
- dependency/security checks;
- formatting verification.

No separate paid CI platform is required for the MVP unless a concrete limitation appears.

## 3. Environment model

The project uses three conceptual environments:

### Development

Local/feature development and experimentation.

### Staging

A **persistent, isolated staging environment** used for release validation. It has its own database and staging media namespace/storage boundary. It must never share production data or production media objects.

The MVP does **not** depend on creating a full temporary preview environment for every Pull Request. Render Preview Environments remain an optional future capability if the project later justifies the cost/complexity.

### Production

The public Explore Luxembourg 360 environment.

## 4. Release flow

```text
Feature branch
      ↓
Pull Request
      ↓
GitHub Actions
      ↓
Lint / Typecheck / Tests / Build
      ↓
PASS
      ↓
Staging deployment
      ↓
Smoke tests
      ↓
Explicit production approval
      ↓
Production deployment
      ↓
Health checks
```

A failed required check blocks progression.

## 5. Production approval gate

Production deployment is a **controlled release**, not an unconditional side effect of every merge.

Before production:

- required CI checks pass;
- staging deployment succeeds;
- smoke tests pass;
- release is explicitly approved.

The exact GitHub/Render mechanism used to implement the approval gate may be selected during bootstrap, but the architectural requirement is fixed.

## 6. Smoke tests

The MVP smoke-test path should validate the critical end-to-end experience:

```text
Homepage
   ↓
API
   ↓
Database
   ↓
Place
   ↓
Experience
   ↓
Media
```

Authentication and Save/Collection smoke tests are added when those capabilities are active in the slice.

## 7. Deployment and rollback

Every deployment must be identifiable by its originating commit/version.

Application rollback must be possible to the last known-good version.

Rollback of application code and rollback of database state are separate operations.

**Never perform an automatic destructive database rollback.**

## 8. Database migrations

Use backward-compatible migration practices, following:

> **Expand → Migrate → Contract**

Where practical, new application code must remain compatible with the previous database shape during rollout. Destructive cleanup happens only after the new version is stable.

## 9. Failure handling

If a deployment fails health checks or smoke tests:

```text
Deployment fails
      ↓
No production traffic to failed version
      ↓
Investigate
      ↓
Fix or rollback application
```

A failed release must not silently replace a healthy production version.

## 10. Secrets

Environment-specific secrets are required for Development, Staging and Production.

Secrets must not be committed to GitHub or exposed to the browser.

Examples include:

- Auth0 secrets;
- database credentials;
- R2 credentials;
- private provider/API credentials.

## 11. Codex compatibility

Codex may work through normal feature branches and Pull Requests.

Codex must not bypass:

- branch protection;
- required CI checks;
- production approval;
- architecture decisions.

Codex must not silently redesign approved Product, Design or Architecture decisions.

## 12. Traceability

A production release must be traceable through:

```text
Pull Request
   ↓
Commit
   ↓
CI result
   ↓
Staging validation
   ↓
Approval
   ↓
Production deployment
```

The team must be able to identify what version is live and which commit produced it.

## 13. Explicit non-goals for MVP

- no separate paid CI/CD platform;
- no per-PR full environment requirement;
- no complex GitOps;
- no Kubernetes;
- no multi-region release orchestration;
- no automatic destructive database rollback;
- no release-management platform unless a concrete need emerges.

## 14. Final decision

**GitHub Actions + protected GitHub workflow + persistent isolated staging + controlled Render production deployment** is the approved target architecture for R5.2.

The implementation remains minimal, auditable and cost-controlled.

# R5.1 — Cloud & Deployment Architecture

**Status:** CLOSED — APPROVED — FINAL AUDIT PASS
**Version:** v1.2 — September 2026

## Objective

Define the smallest credible production infrastructure for Explore Luxembourg 360: secure, observable, recoverable, cost-conscious, and compatible with the approved application stack.

## Approved direction

- **Cloudflare:** DNS, HTTPS, edge/network layer, CDN/controlled caching, security controls, and R2 media delivery.
- **Render:** initial application runtime for Next.js, NestJS/Node.js, and managed PostgreSQL + PostGIS.
- **Auth0:** user identity and authentication.
- **R2:** primary media/object storage, with public/private separation and versioned/immutable public asset keys.
- **Backups:** managed PostgreSQL production backup/recovery plus R2 as primary media storage.
- **Future archive:** Backblaze B2 may be introduced later for a second copy/archive of important originals; it is not an MVP dependency.

## Environment model

1. Development — local/branch development.
2. Staging — automated build/deployment and validation before public release.
3. Production — live public environment.

## CI/CD

GitHub is the source of truth. Automated checks should cover linting, type checking, tests and build. Render handles application deployment from the approved Git flow. Production releases require successful staging/smoke validation.

## Health & observability

MVP minimum:
- `/api/health` and `/api/ready` health endpoints;
- application/access/error logs;
- basic error monitoring.

Advanced tracing and observability are future scope.

## Rollback

Application rollback must be possible to a known deployment/version. Database migrations must be backward-compatible where practical. Destructive automatic database rollback is explicitly prohibited; database recovery is a separate controlled operation.

## Security

Required baseline:
- HTTPS;
- secrets outside source code/client bundles;
- least privilege;
- server-side validation;
- protected database;
- private originals and unpublished media;
- secure uploads;
- rate limiting where appropriate;
- controlled deployments;
- backups and recovery.

Cloudflare edge security/WAF/rate limiting are treated as capabilities to configure according to actual plan and need; the architecture does not assume every advanced feature is active by default.

## CDN / caching rule

Use **Cloudflare edge/CDN with controlled caching**. Public, immutable/versioned media can be cached aggressively. Authenticated, personalised, or sensitive responses must not be cached indiscriminately.

## PostgreSQL production rule

Production must use a managed paid PostgreSQL tier appropriate to the project, with backup/recovery capability. Free/test database tiers are not considered the production recovery strategy.

## Privacy / EU baseline

Use EU-first data placement where appropriate, minimise personal data collection, define retention/deletion rules, review subprocessors and DPAs before public production, and keep personal/authenticated data logically separated from public editorial media.

## Offline boundary

The MVP is **online-first and offline-aware**, with useful local cache, graceful degradation, retry/reconnection and preservation of locally available state where practical. The minimum offline resilience boundary is defined in **R5.6**. Full downloadable experiences, dedicated offline maps/navigation, complex offline synchronisation, offline uploads and advanced offline media remain future scope.

## Explicitly out of MVP

- Kubernetes / complex orchestration;
- complex microservices;
- multi-region infrastructure;
- data lake;
- advanced distributed tracing;
- full offline infrastructure;
- Cloudflare Workers rewrite of the NestJS backend solely for infrastructure optimisation.

## Guiding principle

> **Smallest Credible Production** — build only the infrastructure required to operate the first real Explore Luxembourg 360 vertical slice safely and recoverably, then scale only when evidence justifies it.

## Final audit result

The architecture and visual demonstration were reviewed against the R5.1 requirements and audit refinements. No blocking architectural issue remains.

- PostgreSQL wording explicitly limits backup/recovery expectations to an appropriate production tier.
- Cloudflare security capabilities are not represented as automatically active regardless of plan.
- CDN behaviour is explicitly controlled to protect personalised/sensitive responses.
- The MVP remains intentionally small, with future capabilities separated from production requirements.
- The offline boundary is explicitly delegated to R5.6, whose MVP scope is offline-aware rather than offline-first.

**R5.1 is CLOSED and APPROVED.**

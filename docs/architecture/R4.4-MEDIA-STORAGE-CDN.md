# R4.4 — Media Storage & CDN

## Status
**REFINED — AWAITING FINAL AUDIT**

## Decision
Cloudflare R2 is the preferred primary object storage and media delivery foundation for Explore Luxembourg 360.

Backblaze B2 is retained as a future strategic backup/archive candidate, not as a required MVP service.

Supabase Storage is not selected for the current media layer because the project does not need another infrastructure platform for this concern and its current pricing model is less aligned with the project's free-first strategy.

## Why this decision fits Explore Luxembourg 360
The project will handle:
- editorial photographs;
- Place / Nature / Heritage imagery;
- user-generated media where supported;
- 360° panoramas and derived tiles;
- video and future 360° video;
- large original field-capture files from the Insta360 X6;
- future 3D-related assets.

Media must therefore be treated as a first-class infrastructure concern while keeping binary assets separate from domain metadata.

## Storage principles
1. PostgreSQL stores media metadata and relationships, not binary media files.
2. Original/master assets are separated from public/derived assets.
3. Public clients receive optimized derivatives rather than field-capture masters.
4. Images should support responsive variants, thumbnails, previews and lazy loading.
5. 360° assets should support progressive/tiled delivery where appropriate.
6. Processing is separated from storage so derived assets can be regenerated.
7. Media storage is accessed through an application-level abstraction rather than provider-specific domain logic.
8. Public and private media use different access policies.
9. The architecture must allow a future storage-provider migration without changing the domain model.
10. Public media should use versioned/immutable asset keys where practical, so replacements do not depend on immediate CDN cache invalidation.

## Originals / field capture
The Insta360 X6 field-capture masters are treated as archival source material.

Capture workflow:

X6 + GPS
→ local master
→ verified backup
→ private object storage
→ processing
→ derived media
→ public delivery

Originals must not be overwritten during processing and must not be served to normal public clients.

## CDN / delivery
Cloudflare R2 is preferred because it can be paired directly with Cloudflare edge caching and custom-domain delivery. R2 currently provides 10 GB/month of free Standard storage, free allowances for Class A/B operations, and zero internet egress charges under its published pricing model. Pricing and limits are time-sensitive and must be rechecked before production implementation.

The application should use caching and appropriate cache-control policies so repeated public media requests are served efficiently from the edge where possible.

For architecture documentation, provider capabilities such as the exact size of the edge network or specific transport protocols are not treated as application requirements; the stable requirement is **Cloudflare edge caching / CDN delivery**.

## Cache and asset versioning
Public media should preferably be published under immutable or versioned storage keys, for example:

image-v1.webp
image-v2.webp

or stable content/version identifiers generated by the media pipeline.

This avoids relying on immediate cache invalidation when a public asset is replaced. Cache purge/invalidation remains an implementation concern for exceptional cases.

## Cost strategy
The project follows a strict free-first / pay-as-you-grow principle.

MVP target:
- R2 as the only required media storage service;
- no mandatory backup subscription;
- no dedicated media-processing subscription unless required;
- use open-source/local processing where practical;
- introduce additional paid infrastructure only when real usage or a concrete requirement justifies it.

## Backblaze B2 future role
Backblaze B2 is retained as a future candidate for:
- second-copy backup of original field captures;
- long-term archive;
- disaster-recovery storage;
- Object Lock / retention protection where appropriate;
- migration insurance if the primary storage provider changes.

B2 is **not** required for MVP and must not create a second monthly cost before the project needs it.

The application should therefore not depend directly on B2. If introduced, it should sit behind the same media/archive abstraction.

## Security
Private originals and non-public media must use controlled access. Where direct temporary access is required, use signed/presigned access mechanisms rather than exposing storage credentials.

Public editorial media may be delivered through public/cacheable URLs where licensing and product policy permit.

Storage credentials must never be exposed in client-side application code.

## Privacy / GDPR
Media metadata and binary assets must have explicit ownership, access, retention and deletion rules before production launch, particularly for user-generated media and any media containing identifiable people or location information.

The storage provider does not remove Explore Luxembourg 360's responsibility for its own GDPR obligations.

## Provider abstraction
The application should expose a provider-neutral media interface conceptually similar to:

MediaStorageAdapter
├── R2 implementation
└── future B2 / other implementation

Domain entities must reference stable Explore 360 media identifiers and metadata rather than hard-coding provider-specific object IDs as the primary identity of an asset.

## 360° requirements
The media layer must support the R4.3 renderer strategy:
- panorama previews;
- optimized panorama delivery;
- tiled/progressive delivery where beneficial;
- metadata required by the renderer;
- future special 360° experiences;
- future 3D assets without requiring a redesign of the media domain.

## Alternatives considered
### Cloudflare R2
Preferred primary option because of its low-cost starting point, zero internet egress, S3-compatible API, Cloudflare edge integration and strong fit for public media delivery.

### Backblaze B2
Preferred future backup/archive candidate because of low storage pricing, S3-compatible API, European storage regions and strong archival features such as Object Lock.

### Supabase Storage
Technically capable and convenient when the entire platform is built around Supabase, but not selected for the current project because it adds less architectural value given the existing direction and its current paid-tier economics are less aligned with the free-first media strategy.

## Decision boundary
This decision does **not** yet lock:
- exact bucket names;
- final CDN cache rules;
- image transformation service;
- video transcoding provider;
- backup frequency;
- retention periods;
- production R2 account configuration.

Those details will be defined during implementation planning and validated against the first real media workload.

## Future validation
The first production-like media test should include:
- normal web image;
- responsive image variants;
- large photograph;
- 360° panorama;
- tiled/progressive 360° asset;
- private original;
- public cached asset;
- deletion/replacement flow;
- realistic mobile network test;
- verification that versioned public keys behave correctly with CDN caching.

## Current conclusion
**R2 is the approved direction for primary media storage and delivery. B2 is retained as a future backup/archive option.**

The R4.4 decision remains open only for final audit and implementation-level validation.

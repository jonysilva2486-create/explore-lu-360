# R4.2 — Authentication Provider

## Status
**REFINED — AWAITING FINAL AUDIT / CLOSE**

## Decision
Auth0 is the preferred initial Identity Provider for Explore Luxembourg 360, subject to final implementation, contractual, privacy and operational validation.

## Core principles
- Accountless exploration first.
- Authentication is required only for persistent user features such as Saves and Collections.
- Explore Luxembourg 360 does not store user passwords.
- Authentication security is delegated to a mature, specialised identity provider rather than implemented in-house.
- Auth0 must remain behind an application authentication boundary so the domain does not depend directly on Auth0-specific types.
- The application retains ownership of its own User, Save, Collection, Preference and other domain data in PostgreSQL.
- Personal data is minimised in the identity provider and in the application database.
- The free-first / cost-controlled strategy applies: no paid authentication tier is assumed while the current Auth0 Free plan satisfies the approved MVP requirements and applicable terms.

## Proposed user flow
Visitor → Explore → Discover → Save → Sign in → Authenticated User → Synchronised data.

Users can explore maps, Places, Routes, Stories, media and Street View without an account. Authentication appears when a persistent action requires it.

## Authentication provider responsibilities
Auth0 is responsible for the identity/authentication layer, including supported credential and identity mechanisms, social login, passwordless/passkey capabilities and authentication security controls selected for the project.

The Explore 360 application remains responsible for authorization, protection of application endpoints, domain-level access control and correct handling of its own personal data.

## Application responsibilities
The application maintains its own domain User and links it to the external identity through a provider adapter. Domain code should use concepts such as User, Identity and Session rather than Auth0-specific objects.

Example:

Auth0 Identity → Explore 360 User → Saves / Collections / Preferences / other application data

Deleting an account must coordinate deletion of both the external identity and the personal data held by Explore 360. Export must likewise cover the application's own data, not merely the identity-provider record.

## GDPR and privacy clarification
Auth0 provides identity-security and privacy capabilities that support Explore Luxembourg 360's GDPR obligations. It does **not** make the application automatically GDPR-compliant. Explore Luxembourg 360 remains responsible for its own GDPR compliance, including lawful basis, transparency, data minimisation, retention, deletion, export, controller/processor responsibilities and applicable contractual arrangements.

The project must not store unnecessary sensitive or personal information in Auth0 merely because the platform permits it.

## Cost model
The current Auth0 Free plan provides up to 25,000 MAU at no charge, subject to the plan's current features, limits and terms. The project does not assume a paid tier during MVP validation.

If usage exceeds the free tier or a paid-only capability becomes necessary, the cost must be explicitly reviewed before adoption. A larger user count does not itself constitute permission to introduce a paid tier without a project-level decision.

## Scalability wording
The architecture is designed to **scale beyond the initial free tier without requiring a change to the application's authentication model**. This is an architectural goal, not a promise of unlimited users at zero cost.

## Custom domain note
Auth0's current Free plan supports custom domains subject to its current requirements; verification may require a payment card even though the Free plan itself has no subscription charge. This is an implementation/setup consideration, not an assumed monthly cost.

## Security boundaries
The project must never:
- store passwords itself;
- implement its own OAuth/OIDC identity system;
- create bespoke credential-recovery infrastructure;
- expose Auth0-specific identities throughout the domain model;
- assume that authentication implies authorization.

The API must validate authenticated identity and enforce authorization for user-owned resources such as Saves and Collections.

## MVP authentication scope
### MUST HAVE
- Email-based authentication.
- At least one major social login path.
- Secure session/token validation.
- Logout.
- Account deletion flow.
- User-data export flow.
- Accountless exploration.
- Save/Collection authentication boundary.
- GDPR/privacy responsibilities documented.

### SHOULD / FUTURE
- Additional social providers.
- Expanded MFA options where justified.
- Advanced enterprise identity features.
- Organisation/enterprise accounts.
- Other Auth0 capabilities that do not directly serve the MVP.

## Alternatives retained
- Supabase Auth remains the strongest strategic alternative if the broader infrastructure direction later adopts Supabase.
- Clerk remains a viable specialised alternative.
- Amazon Cognito remains viable if R5 establishes an AWS-first infrastructure direction.

These alternatives do not alter the current preferred decision.

## Final audit refinements incorporated
1. Replace any wording suggesting “millions of users without rearchitecting” with the more precise architectural statement above.
2. Explicitly state that Auth0 supports our GDPR obligations but does not transfer legal compliance responsibility away from Explore Luxembourg 360.
3. Treat the Auth0 Free-plan limits, features and terms as time-sensitive assumptions that must be revalidated at implementation time.

## Closing criterion
R4.2 can be closed after final audit confirms the refined wording, the Auth0 Free-plan assumptions, privacy/contractual validation and the implementation boundary described above.

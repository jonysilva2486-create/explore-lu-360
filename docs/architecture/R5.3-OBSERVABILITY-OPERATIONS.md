# Explore Luxembourg 360 — R5.3 Observability & Operations

**Status:** REFINED — READY FOR FINAL AUDIT  
**Version:** v1.1 — August 2026

## Purpose

Define the smallest credible observability and operations layer for the first vertical slice so the team can know whether the system is healthy, understand important failures, recover safely, and do so without unnecessary user monitoring or recurring tooling costs.

## Core principle

> **Observe the system, not the user.**

Observability exists to operate the product safely. It must not become a mechanism for unnecessary surveillance or collection of personal data.

## 1. Native-first observability

Use capabilities already provided by the approved infrastructure before adding specialist platforms.

### Render

Primary MVP source for:

- health checks;
- readiness checks;
- application/service logs;
- service metrics;
- database metrics;
- deployment history.

### Cloudflare

Primary edge/storage operational layer for:

- DNS/edge visibility;
- relevant security signals;
- R2 audit logs for bucket configuration changes.

Cloudflare Workers-specific observability is not an MVP dependency because the approved architecture does not require the application backend to run on Workers.

### External uptime monitor

Use an independent external monitor for public availability. The MVP target is a free-tier monitor such as UptimeRobot with a 5-minute interval.

### Sentry

**SHOULD, not MUST.** Sentry may be introduced when application error context becomes materially useful beyond Render logs. It is not a required MVP dependency.

## 2. Health and readiness

The application should expose:

- `/health` — basic liveness;
- `/ready` — readiness of the application and critical dependencies.

Health checks answer whether the service is alive. Readiness answers whether it is ready to serve traffic.

## 3. Structured logging

Application logs should be structured and searchable where practical, with fields such as:

- timestamp;
- service;
- environment;
- severity;
- event;
- request/correlation identifier;
- relevant non-sensitive entity identifier;
- duration;
- sanitized error information.

Never log passwords, secrets, access tokens, refresh tokens, or unnecessary personal data.

## 4. Privacy-safe observability

The application is responsible for sanitising telemetry before it reaches Render, Sentry, or any other external monitoring destination.

Observability systems must not become secondary stores of unnecessary personal information.

Minimum-data principle:

> **If operationally useful data can be collected without identifying a person, prefer the non-identifying form.**

## 5. Monitoring scope

The MVP monitors:

- system health;
- infrastructure/service health;
- application errors;
- database health;
- public availability;
- critical media/360 delivery failures;
- deployment health.

It does not attempt to monitor users as individuals.

## 6. External dependencies

Only critical external dependencies receive explicit operational treatment in the MVP.

The application should distinguish provider failures from internal failures where practical, including dependencies such as:

- Auth0;
- Google services used by the approved integration;
- Géoportail, once integrated;
- Cloudflare/R2.

No separate synthetic monitor is required for every provider endpoint in the MVP. Provider errors should be observable through application error handling and logs.

## 7. 360/media delivery monitoring

Published 360 experiences require a lightweight synthetic verification strategy.

The MVP should verify representative published assets rather than continuously probing every tile/file.

A future synthetic check may validate:

```text
Experience
   ↓
360 manifest / entry point
   ↓
Representative asset(s)
   ↓
HTTP success / expected response
```

An isolated media failure is an error; widespread media failure may become critical depending on impact.

## 8. Alerting

Alerts are severity-based and intentionally limited.

| Event | Severity | Alert | Channel / owner |
|---|---|---|---|
| Health check failure / site down | Critical | Yes | Email/Webhook — Owner/On-call |
| Database unavailable | Critical | Yes | Email/Webhook — Owner/On-call |
| Major API error spike | Critical | Yes | Email/Webhook — Owner/On-call |
| Deployment failure | Error | Yes | Email/Webhook — Owner/Dev |
| Major feature failure | Error | Yes | Email/Webhook — Owner/Dev |
| Isolated 360/media error | Error | Yes | Email — Owner/Dev |
| High response time | Warning | No by default | Dashboard — Dev/Ops |
| High CPU/memory | Warning | No by default | Dashboard — Dev/Ops |
| Normal informational log | Info | Never | Dashboard |

The exact channel/provider may evolve, but the severity policy is fixed.

## 9. Availability monitoring

An external uptime monitor provides an independent view of public availability.

The MVP target is a free-tier monitor using a 5-minute check interval. A faster interval is not required until the project's operational needs justify the additional cost.

## 10. Error monitoring

Render logs are the baseline MVP error source.

Sentry remains a SHOULD and may be enabled when:

- error volume or complexity increases;
- stack/context information materially improves diagnosis;
- the project can use an appropriate free/paid tier without compromising cost discipline.

If enabled, Sentry must follow the same privacy-safe telemetry rules.

## 11. Database monitoring

Use Render's managed PostgreSQL metrics for the MVP, including relevant connection, query, lock, replication, and resource indicators available to the selected production tier.

No Prometheus/Grafana stack is required for MVP.

## 12. Application audit trail

Provider audit logs and application audit logs are separate concerns.

### Provider audit logs

Cloudflare/R2/Render logs cover infrastructure or provider-level changes where supported.

### Application audit trail

When the Explore 360 admin layer exists, the application itself must record critical administrative actions such as:

- publishing/unpublishing content;
- deleting important content;
- changing important permissions;
- other security-sensitive administrative actions.

Only the minimum information needed for accountability should be retained.

## 13. Incident procedure

For significant incidents:

```text
DETECT
  ↓
ASSESS
  ↓
CONTAIN
  ↓
RECOVER
  ↓
VERIFY
  ↓
DOCUMENT
```

The MVP does not require a large incident-management platform.

## 14. Recovery verification

After a fix or rollback:

- verify health;
- verify readiness;
- run the relevant smoke checks;
- confirm the affected experience is functional;
- continue monitoring for recurrence.

## 15. Log retention

Use the retention provided by the selected Render production tier initially. Do not introduce external log archival merely for theoretical future needs.

Longer retention or external log streaming may be added when operational, legal, or analytical requirements justify it.

## 16. Cost strategy

No new mandatory observability subscription is required for the MVP.

Use native/free capabilities first:

- Render native observability;
- Cloudflare/R2 native operational visibility;
- free-tier external uptime monitoring;
- Sentry only when justified.

**Production infrastructure (including Render services and managed database) remains separately budgeted and is not represented as a €0/month production stack.**

## 17. Codex compatibility

Observability complements the R5.2 delivery pipeline:

```text
Codex / Developer
      ↓
Pull Request
      ↓
CI
      ↓
Staging
      ↓
Production approval
      ↓
Production
      ↓
Observability
```

CI prevents known defects from reaching production. Observability detects issues that only become visible under real production conditions.

## 18. Explicit non-goals for MVP

- no Datadog/New Relic-style full observability suite;
- no mandatory Sentry dependency;
- no Prometheus/Grafana stack;
- no distributed tracing;
- no predictive monitoring;
- no complex dashboards;
- no per-asset continuous media probing;
- no synthetic monitoring of every external API;
- no unnecessary user-level tracking;
- no mandatory new observability subscription.

## 19. Decision

**Native-first observability using Render + Cloudflare/R2 + external uptime monitoring, with Sentry as an optional SHOULD, is the approved target direction for R5.3, subject to final audit.**

The implementation remains minimal, privacy-safe, operationally useful, and cost-controlled.

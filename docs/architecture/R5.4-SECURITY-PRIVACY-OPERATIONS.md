# Explore Luxembourg 360 — R5.4 Security & Privacy Operations

**Status:** REFINED — READY FOR FINAL AUDIT  
**Version:** v1.1 — August 2026

## Purpose

Define the security and privacy baseline for the first vertical slice, using the approved infrastructure first and adding specialist controls only when a concrete risk, scale or compliance requirement justifies them.

## Core principles

- **Least privilege** — each component receives only the access it needs.
- **Server-side trust** — security and authorization decisions are made by the backend.
- **Data minimization** — collect only what is necessary.
- **Secure by default** — safe defaults are the baseline.
- **Provider-first security** — use Auth0, Cloudflare, Render, R2 and GitHub capabilities first.
- **No security theater** — do not add tools merely to appear enterprise-grade.
- **Cost-aware security** — essential security is mandatory, specialist tooling is justified by concrete risk or scale.

## 1. Identity & Authentication

Auth0 is the identity provider. The project does not implement password storage itself.

MUST:
- secure session handling;
- server-side access-token validation;
- account recovery;
- logout/revocation strategy;
- secure token configuration.

SHOULD for normal users:
- MFA capability;
- refresh-token rotation where applicable.

MUST for administrative accounts when the admin layer exists:
- MFA;
- stronger session controls;
- secure recovery path.

## 2. Authorization & Object Access

Authentication and authorization are separate concerns.

The API must perform server-side authorization for every protected operation, including resource ownership checks and administrative permissions.

**Broken Object-Level Authorization / IDOR prevention is explicit MUST:** every object-level read/write/delete operation must verify ownership or explicit authorization for that resource.

Client-side hiding of controls is never considered a security boundary.

## 3. Secrets

Secrets remain outside source control and are separated by environment.

Production credentials must not be exposed to the browser, committed to GitHub, or written to logs.

Examples: Auth0 secrets, database credentials, R2 credentials and private provider/API credentials.

Codex development environments must never receive production credentials.

## 4. API Security

MUST include:
- input/schema validation;
- server-side authorization;
- IDOR/BOLA protection;
- safe error responses;
- request/body and response-size limits;
- pagination/resource limits;
- protection against mass assignment;
- abuse/rate protection where justified;
- protection of administrative and upload endpoints;
- SSRF protections for any future server-side URL fetching/import feature;
- explicit CSRF assessment for the selected authentication/session model.

No raw SQL may be constructed from untrusted input; parameterized queries are required.

## 5. Web Security

MUST include:
- output encoding;
- sanitization of rich/user-provided content;
- Content-Security-Policy;
- HSTS where applicable;
- X-Content-Type-Options;
- Referrer-Policy;
- Permissions-Policy;
- appropriate frame protection;
- secure cookie attributes where cookies are used;
- controlled CORS.

Unsafe HTML rendering is prohibited by default.

## 6. Upload Security

Uploads are never published directly.

```text
Upload → Validate → Process → Review/Control → Publish
```

MUST:
- validate actual file content/type, not extension alone;
- enforce file-size and processing/resource limits;
- sanitize filenames;
- use an isolated/private upload boundary;
- controlled publication;
- protect image/video/3D processing from resource exhaustion;
- reject unsupported active/scriptable formats unless explicitly required.

Where images are processed, EXIF/GPS metadata handling must be explicitly defined before public publication.

Malware scanning is SHOULD/future until user-generated uploads and risk justify a dedicated scanning capability.

## 7. R2 / Media Security

Published public media and unpublished/private media must be logically separated.

Use R2 access controls, restrictive CORS and short-lived presigned URLs where direct temporary access is required.

Presigned URLs must be:
- object-specific;
- operation-specific;
- short-lived;
- constrained by content type where appropriate;
- never logged in full.

R2 credentials must never be exposed to clients.

## 8. Database Security

PostgreSQL/PostGIS must:
- use encrypted connections;
- remain inaccessible directly from the browser;
- use least-privilege application credentials;
- use private/internal connectivity where available;
- keep production/staging separated;
- follow controlled migrations and approved backup/recovery procedures.

Production external database access should be disabled unless there is a documented operational requirement.

Database migration credentials/processes must be separated from the normal application role where practical.

## 9. Edge Security & Cloudflare

Cloudflare is the first public security boundary.

### Development / Staging

Use the applicable Free-tier baseline.

### Public Production

The project intends to upgrade the primary public application zone to **Cloudflare Pro** when production goes live, subject to confirming the current plan features and pricing at that time.

Budget assumption for planning: approximately **$25/month when billed monthly or $20/month equivalent when billed annually**, subject to provider pricing changes.

Cloudflare Pro is an additional defence layer, not a replacement for application security.

The implementation must minimize direct origin exposure. Where supported by the final Cloudflare/Render configuration, direct origin access should be restricted so Cloudflare is the intended public entry point.

Advanced WAF/rate-limiting capabilities remain plan-dependent and are never assumed to be free.

## 10. GitHub / Supply Chain Security

Use repository-native capabilities where available:
- dependency/vulnerability checks;
- secret scanning;
- code scanning;
- lockfile enforcement;
- controlled dependency updates;
- pinned/controlled runtime versions.

Adding a dependency that handles authentication, security, data or infrastructure requires review.

Automatic blind dependency upgrades are prohibited.

No separate security SaaS is mandatory for MVP.

## 11. Privacy & GDPR Governance

Security and privacy architecture must include a documented data inventory covering:
- data category;
- purpose;
- legal basis;
- storage location;
- processor/provider;
- access;
- retention;
- deletion/lifecycle.

The project must maintain a provider/processor inventory and assess applicable data-processing agreements and international transfer mechanisms before production processing of personal data.

The project must provide an appropriate privacy notice and define processes for applicable data-subject rights, including access, rectification, deletion and portability where applicable.

This is an architectural/operational requirement; legal implementation details may require qualified professional review before public launch.

## 12. Cookies & Tracking

Essential authentication/session mechanisms are separated from optional analytics or marketing tracking.

Marketing tracking is not part of the MVP by default.

Analytics must not become individual profiling by default and must be evaluated separately from observability.

## 13. Retention & Deletion

Retention must be defined by data category.

Account deletion must define the treatment of profile data, saved places/collections, user uploads, authentication identity and any records that have a legitimate security/legal retention basis.

Operational logs must be retained only as long as justified.

## 14. Administrative Security & Audit

When the administrative layer exists:
- MFA is mandatory;
- least-privilege roles are mandatory;
- sensitive actions require server-side authorization;
- critical actions may require re-authentication;
- publish, unpublish, delete, permission changes and account moderation must be auditable.

Application audit trails are separate from Render/Cloudflare provider audit logs.

## 15. Security Incident Response

Minimum procedure:

```text
Detect → Contain → Preserve Evidence where appropriate → Assess → Eradicate → Recover → Review
```

Critical incidents include suspected credential compromise, unauthorized data exposure, malicious upload, account compromise and significant API abuse.

A technical incident must be separately assessed for whether it constitutes a personal-data breach and whether notification obligations apply.

## 16. Credential Rotation

If a credential is suspected compromised:

```text
Revoke → Generate new secret → Update environment → Deploy → Verify → Review
```

Maintain a rotation/revocation matrix covering Auth0, Render, R2, GitHub and Cloudflare credentials/tokens as applicable.

Rotation is mandatory whenever compromise is suspected.

## 17. Backup Security

Backups must have:
- restricted access;
- encryption where provided;
- separate credentials/access controls;
- defined retention;
- production/staging separation;
- documented restore testing.

A backup that has never been restored successfully is not considered a verified recovery strategy.

## 18. Security Testing

Before the first public production release, the security test baseline must cover at minimum:

```text
Authentication
Authorization
IDOR / BOLA
XSS
CSRF (according to session model)
SQL injection
SSRF protections where applicable
Upload abuse/resource exhaustion
Rate limiting / abuse controls
Access control
Secret leakage
Security headers
CORS
```

Future:
- penetration testing;
- external security audit;
- advanced DAST;
- threat simulation.

## 19. Threat Model

Primary threat actors:
- malicious users;
- compromised accounts;
- automated bots;
- malicious uploaders;
- compromised dependencies;
- stolen credentials;
- external provider incidents;
- accidental insider/admin actions.

Protected assets:
- accounts;
- personal data;
- unpublished content;
- 360 media;
- administrative access;
- database;
- infrastructure.

## 20. Codex Security Boundary

Codex may modify code and tests through the normal branch/PR workflow.

Codex must not:
- bypass branch protection;
- disable CI/security checks;
- access production credentials from development environments;
- expose secrets;
- remove authorization controls;
- alter approved privacy/security policy without review;
- bypass production approval.

## 21. Specialist Tooling Decision

No dedicated security platform is mandatory for MVP.

Approved baseline:

```text
Auth0      → Identity / authentication
Cloudflare → Edge security
Render     → Runtime / TLS / secrets / private connectivity
R2         → Media access control
Postgres   → Protected data layer
GitHub     → Source / dependency / code security
```

Sentry remains an application-observability decision under R5.3, not the primary security perimeter.

Specialist tooling such as dedicated malware scanning, Snyk/Aikido, SIEM, advanced WAF, penetration testing or external security audit is introduced only when a concrete risk, scale or compliance requirement justifies it.

## 22. Cost Principle

R5.4 introduces **no mandatory specialist security subscription during development/staging**.

For public production, **Cloudflare Pro is an approved planned security upgrade**, currently budgeted at approximately $25/month monthly or $20/month equivalent annually, subject to current provider pricing at implementation time.

This cost is separate from core production infrastructure and does not replace the mandatory application-level security controls in this document.

## Final decision

**Provider-first Security + production Cloudflare Pro hardening** is the approved R5.4 target architecture.

The project will not equate a paid security layer with complete security. Application, identity, privacy, data and operational controls remain mandatory.

# Explore Luxembourg 360 — R5.4 Security & Privacy Operations

**Status:** APPROVED — READY FOR AUDIT
**Version:** v1.0 — August 2026

## Purpose

Define the smallest credible security and privacy baseline for the first vertical slice, using the capabilities already present in the approved architecture before introducing specialist security tooling.

## Core principles

- **Least privilege** — each component receives only the access it needs.
- **Server-side trust** — the backend makes security and authorization decisions.
- **Data minimization** — collect only what is necessary.
- **Secure by default** — safe defaults are the baseline.
- **Provider-first security** — use Auth0, Cloudflare, Render, R2 and GitHub capabilities first.
- **No security theater** — do not add tools merely to appear enterprise-grade.
- **Cost-aware security** — essential security is mandatory, but specialist tooling must have a concrete justification.

## 1. Identity & Authentication

Auth0 is the identity provider. The project does not implement password storage itself.

MUST:
- secure session handling;
- server-side access-token validation;
- account recovery;
- logout/revocation strategy;
- secure token configuration.

SHOULD:
- MFA capability;
- refresh-token rotation where applicable.

## 2. Authorization

Authentication and authorization are separate concerns.

The API must perform server-side authorization for every protected operation, including resource ownership checks and administrative permissions.

Client-side hiding of controls is never considered a security boundary.

## 3. Secrets

Secrets remain outside source control and are separated by environment.

Production credentials must not be exposed to the browser, committed to GitHub, or written to logs.

Examples: Auth0 secrets, database credentials, R2 credentials and private provider/API credentials.

## 4. API Security

MUST include:
- input/schema validation;
- server-side authorization;
- safe error responses;
- request/body size limits;
- abuse/rate protection where justified;
- protection of administrative and upload endpoints.

Cloudflare provides the edge baseline; application-level controls remain the API's responsibility.

## 5. Upload Security

Uploads are never published directly.

```text
Upload → Validate → Process → Review/Control → Publish
```

MUST:
- file type/content validation;
- file size limits;
- filename sanitization;
- isolated/private upload boundary;
- controlled publication.

Malware scanning is a SHOULD/future capability to be introduced when user-generated uploads and risk justify it.

## 6. R2 / Media Security

Published public media and unpublished/private media must be logically separated.

Use R2 access controls, CORS restrictions and short-lived presigned URLs where direct temporary access is required. R2 credentials must never be exposed to clients.

## 7. Database Security

PostgreSQL/PostGIS must:
- use encrypted connections;
- remain inaccessible directly from the browser;
- use least-privilege credentials;
- use private/internal connectivity where available;
- maintain production/staging separation;
- follow controlled migrations and approved backup/recovery procedures.

## 8. Edge Security

Cloudflare is the first public security boundary.

The baseline uses applicable Free-tier capabilities first, including HTTPS/TLS, DDoS protection, available managed rules, custom rules and the available rate-limiting capability.

Advanced WAF/rate-limiting capabilities remain plan-dependent and are not assumed to be free.

## 9. GitHub / Code Security

Use repository-native capabilities where available:
- dependency/vulnerability checks;
- secret scanning;
- code scanning where available;
- lockfile and controlled dependency updates.

No separate security SaaS is mandatory for MVP.

## 10. Privacy & Data Minimization

The project must document what personal data is collected, why it is needed, where it is stored, who can access it and how long it is retained.

Observability must not collect unnecessary personal data. Passwords, tokens and secrets must never enter logs.

Analytics is a separate concern from observability and must not become individual profiling by default.

## 11. Retention & Deletion

Retention must be defined by data category.

Account deletion must define the treatment of associated user data and content rather than merely hiding an account from the interface.

Logs and operational data should be retained only as long as operationally justified.

## 12. Cookies & Tracking

Essential cookies/session mechanisms are separated from optional analytics or marketing tracking.

Marketing tracking is not part of the MVP by default.

## 13. Security Incident Response

Minimum procedure:

```text
Detect → Contain → Assess → Eradicate → Recover → Review
```

Critical incidents include suspected credential compromise, unauthorized data exposure, malicious upload, account compromise and significant API abuse.

## 14. Credential Rotation

If a credential is suspected compromised:

```text
Revoke → Generate new secret → Update environment → Deploy → Verify
```

Rotation is a SHOULD operational procedure for MVP and becomes mandatory whenever compromise is suspected.

## 15. Dependency Security

Dependencies must use a lockfile and controlled updates. Security updates should be evaluated through the same CI/release gates defined in R5.2.

Automatic blind upgrades are prohibited.

## 16. Security Testing

MVP baseline:
- authentication tests;
- authorization tests;
- input validation tests;
- upload security tests;
- basic abuse/rate-limit tests;
- dependency/security scanning.

Future:
- penetration testing;
- external security audit;
- advanced DAST;
- threat simulation.

## 17. Administrative Security

When the administrative layer exists, sensitive actions must be server-authorized and auditable, including publish, unpublish, delete, permission changes and account moderation.

Application audit trails are separate from Render/Cloudflare provider audit logs.

## 18. Codex Security Boundary

Codex may modify code and tests through the normal branch/PR workflow.

Codex must not bypass branch protection, CI/security checks, production approval, secrets controls or approved architecture/privacy decisions.

## 19. Threat Model

Primary threat actors:
- malicious users;
- compromised accounts;
- automated bots;
- malicious uploaders;
- compromised dependencies;
- stolen credentials;
- external provider incidents.

Protected assets:
- accounts;
- personal data;
- unpublished content;
- 360 media;
- administrative access;
- database;
- infrastructure.

## 20. Tooling Decision

No additional dedicated security platform is required for the MVP.

Approved baseline:

```text
Auth0      → Identity / authentication
Cloudflare → Edge security
Render     → Runtime / TLS / secrets / private connectivity
R2         → Media access control
Postgres   → Protected data layer
GitHub     → Source / dependency / code security
```

Specialist tooling such as dedicated malware scanning, advanced WAF, Snyk, SIEM, penetration testing or external security audit is introduced only when a concrete risk, scale or compliance requirement justifies it.

## 21. Cost Principle

R5.4 introduces **no new mandatory security subscription** for the MVP.

This does not mean production infrastructure is free; it means security tooling is primarily provided by the already-approved stack and applicable free/native capabilities.

## Decision

**Provider-first Security** is the approved R5.4 target architecture, subject to final audit.

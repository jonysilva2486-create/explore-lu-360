# Explore Luxembourg 360 — R5.4 Security & Privacy Operations

**Status:** CLOSED — APPROVED — FINAL AUDIT PASS  
**Version:** v1.3 — August 2026

## Purpose

Define the security and privacy baseline for the first vertical slice, using the approved infrastructure first and adding specialist controls only when a concrete risk, scale or compliance requirement justifies them.

## Final decision

**Provider-first Security + production Cloudflare Pro hardening** is the approved R5.4 target architecture.

The project will not equate a paid security layer with complete security. Application, identity, privacy, data and operational controls remain mandatory.

## Core principles

- **Least privilege** — each component receives only the access it needs.
- **Server-side trust** — security and authorization decisions are made by the backend.
- **Data minimization** — collect only what is necessary.
- **Secure by default** — safe defaults are the baseline.
- **Provider-first security** — use Auth0, Cloudflare, Render, R2 and GitHub capabilities first.
- **No security theater** — do not add tools merely to appear enterprise-grade.
- **Cost-aware security** — essential security is mandatory, specialist tooling is justified by concrete risk or scale.

## Security baseline

### Identity & Authentication
Auth0 is the identity provider. The project does not implement password storage itself.

MUST:
- secure session handling;
- server-side access-token validation;
- account recovery;
- logout/revocation strategy;
- secure token configuration.

For normal users, MFA capability and refresh-token rotation are SHOULD controls where applicable. For administrative accounts, MFA, stronger session controls and a secure recovery path are MUST controls.

### Authorization & Object Access
The API must perform server-side authorization for every protected operation. Every object-level read/write/delete operation must verify ownership or explicit authorization for that resource. Broken Object-Level Authorization / IDOR is an explicit release-gate test.

### Secrets
Secrets remain outside source control and are separated by environment. Production credentials must never be exposed to the browser, committed to GitHub or written to logs. Codex development environments must never receive production credentials.

### API & Web Security
MUST include input/schema validation, server-side authorization, IDOR/BOLA protection, safe errors, request/response resource limits, mass-assignment protection, abuse/rate protection where justified, upload/admin endpoint protection, SSRF protections for future server-side URL fetching, and an explicit CSRF assessment for the selected session model.

Web security must include output encoding, rich-content sanitization, CSP, HSTS where applicable, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, frame protection, secure cookie attributes where cookies are used, and controlled CORS. Unsafe HTML rendering is prohibited by default.

No raw SQL may be constructed from untrusted input; parameterized queries are required.

### Upload / 360 / Future 3D Security
Uploads follow:

```text
Upload → Validate → Process → Review/Control → Publish
```

Actual file content/type, size, filename and processing/resource limits must be validated. Uploads remain isolated/private until controlled publication. Unsupported active/scriptable formats are rejected unless explicitly required. EXIF/GPS metadata handling must be defined before public publication. Dedicated malware scanning remains a future SHOULD until risk/scale justifies it.

### R2 / Media Security
Published and unpublished media are logically separated. R2 access controls, restrictive CORS and short-lived presigned URLs are used where appropriate. Presigned URLs are object-specific, operation-specific, short-lived, constrained by content type where appropriate, and never logged in full. R2 credentials never reach clients.

### Database
PostgreSQL/PostGIS uses encrypted connections, least-privilege application credentials and private/internal connectivity where available. Production external database access should be disabled unless operationally required. Production/staging remain separated. Migration credentials/processes are separated from the normal application role where practical.

### Edge / Cloudflare
Cloudflare is the first public security boundary.

Development/staging use the applicable Free-tier baseline. Public production is planned to use Cloudflare Pro, subject to confirming current provider pricing/features at implementation time. Planning budget: approximately $25/month monthly or $20/month equivalent annually.

Cloudflare Pro is an additional defence layer, not a replacement for application security. Direct origin exposure must be minimized and, where supported by the final Cloudflare/Render configuration, restricted so Cloudflare is the intended public entry point. Advanced WAF/rate-limiting capabilities remain plan-dependent.

### GitHub / Supply Chain
Use repository-native dependency/vulnerability checks, secret scanning, code scanning where available, lockfile enforcement, controlled dependency updates and pinned/controlled runtime versions. Security-sensitive dependencies require review. Blind automatic upgrades are prohibited.

### Privacy & GDPR Governance
Before public production, maintain a data inventory covering category, purpose, legal basis, storage, provider/processor, access, retention and deletion/lifecycle. Maintain a provider/processor register and assess applicable DPAs and international transfer mechanisms. Provide an appropriate privacy notice and operational processes for applicable data-subject rights.

Before public production, perform and document **DPIA screening**. Complete a full DPIA when processing is likely to result in high risk to individuals' rights and freedoms or where otherwise legally required. Legal implementation details may require qualified professional review.

### Cookies / Tracking
Essential authentication/session mechanisms are separated from optional analytics/marketing. Marketing tracking is not part of the MVP by default. Analytics must not become individual profiling by default.

### Retention / Deletion
Retention is defined by data category. Account deletion must define the treatment of profile data, saved places/collections, user uploads, authentication identity and records with a legitimate security/legal retention basis. Operational logs are retained only as justified.

### Administrative Security
When the administrative layer exists: MFA, least-privilege roles and server-side authorization are mandatory. Critical actions may require re-authentication. Publish, unpublish, delete, permission changes and account moderation must be auditable.

### Incident & Breach Response
Minimum procedure:

```text
Detect → Contain → Preserve Evidence where appropriate → Assess → Eradicate → Recover → Review
```

A technical incident is separately assessed for whether it constitutes a personal-data breach and whether notification obligations apply. Where applicable under GDPR, a notifiable breach must be assessed and, where required, notified to the competent supervisory authority without undue delay and, where feasible, within 72 hours of awareness. Where legally required due to high risk, affected individuals must also be informed.

The incident record must capture discovery time, assessment, containment, affected systems/data, notification decision, communications and corrective actions.

### Credential Rotation
Maintain a rotation/revocation matrix for Auth0, Render, R2, GitHub and Cloudflare credentials/tokens as applicable. Suspected compromise triggers:

```text
Revoke → Generate new secret → Update environment → Deploy → Verify → Review
```

### Backup / Recovery
Backups require restricted access, encryption where provided, separate credentials/access controls, defined retention, production/staging separation and documented restore testing. A backup that has never been successfully restored is not a verified recovery strategy.

### Security Testing
Before first public production release, test at minimum:

```text
Authentication
Authorization
IDOR / BOLA
XSS
CSRF (according to session model)
SQL injection
SSRF protections where applicable
Upload abuse/resource exhaustion
Rate limiting / abuse controls
Access control
Secret leakage
Security headers
CORS
```

Future controls may include penetration testing, external security audit, advanced DAST and threat simulation.

### Data-Subject Request Operations
Applicable requests follow:

```text
Request received → Identity verification → Scope/legal assessment → Locate data → Respond/action → Record completion
```

Requests are handled within applicable legal limits, with the GDPR one-month response period targeted where applicable and lawful extensions/refusals documented. Fulfillment must not expose another individual's personal data.

### Provider / International Transfer Register
Before public production, maintain a current register of providers processing personal data, including service, data categories, purpose, role, DPA/contract status, processing/transfer locations, transfer mechanism, retention/deletion behavior and security controls.

### Threat Model
Threat actors include malicious users, compromised accounts, bots, malicious uploaders, compromised dependencies, stolen credentials, external provider incidents and accidental insider/admin actions. Protected assets include accounts, personal data, unpublished content, 360 media, administrative access, database and infrastructure.

### Codex Security Boundary
Codex may modify code/tests through the normal branch/PR workflow but must not bypass branch protection, disable CI/security checks, access production credentials from development environments, expose secrets, remove authorization controls, alter approved privacy/security policy without review or bypass production approval.

## Specialist Tooling Decision

No dedicated security platform is mandatory for MVP. Approved baseline:

```text
Auth0      → Identity / authentication
Cloudflare → Edge security
Render     → Runtime / TLS / secrets / private connectivity
R2         → Media access control
Postgres   → Protected data layer
GitHub     → Source / dependency / code security
```

Sentry remains an application-observability decision under R5.3, not the primary security perimeter. Specialist tooling such as dedicated malware scanning, Snyk/Aikido, SIEM, advanced WAF, penetration testing or external security audit is introduced only when a concrete risk, scale or compliance requirement justifies it.

## Cost Principle

R5.4 introduces **no mandatory specialist security subscription during development/staging**.

For public production, **Cloudflare Pro is an approved planned security upgrade**, currently budgeted at approximately $25/month monthly or $20/month equivalent annually, subject to current provider pricing at implementation time.

This cost is separate from core production infrastructure and does not replace mandatory application-level security controls.

# Explore Luxembourg 360 — R5.5 Backup, Recovery & Rollback

**Status:** CLOSED — APPROVED — FINAL AUDIT PASS  
**Version:** v1.2 — August 2026

## Purpose

Define a practical, recoverable and cost-conscious strategy for application recovery, authoritative data recovery, and protection of irreplaceable Explore 360 media.

## Core principles

- **Backup ≠ Recovery ≠ Rollback.**
- **Irreplaceable masters receive stronger protection than regenerable derivatives.**
- **An offline physical copy is a valid third-copy strategy.**
- **Version history is not a backup.**
- **Recovery is only considered valid after successful restore testing.**
- **No single provider or operational copy should be the sole recovery path for authoritative data or irreplaceable media.**

## 1. Protection Scope

### Tier 1 — Critical

PostgreSQL/PostGIS authoritative data, including Places, Routes, Experiences, Stories, media metadata, users, collections and geographic data.

### Tier 2 — Irreplaceable / High Value

Original 360 masters, original photographs, source video and future 3D capture masters. These must not be considered safely archived until an independent verified copy exists.

### Tier 3 — Regenerable

Thumbnails, tiles, caches and other derivatives that can be recreated from protected masters.

## 2. PostgreSQL Backup Strategy

Production PostgreSQL must use the managed backup/PITR capability provided by the selected production database plan.

The initial production target is:
- PITR enabled where the selected plan supports it;
- **at least one independent encrypted logical export per 24-hour period**;
- backup/export failure must be detectable and actionable;
- defined retention must be documented;
- restore testing must be performed periodically.

The **RPO target is ≤24 hours** for authoritative application data. A stronger RPO may be adopted later if justified by usage and cost.

The independent export is not considered complete until it has been written to a separately controlled backup location and its integrity has been verified.

## 3. Independent PostgreSQL Export — MVP

During MVP, the independent export destination must be a separately controlled object-storage location with access restricted to backup/recovery operations. The preferred low-complexity option is a **dedicated private backup area/bucket with lifecycle controls**, kept logically separate from public application media.

For clarity, a separately controlled location within the same provider is **not** considered provider-independent disaster recovery. The MVP baseline provides logical/access separation; a future second-provider archive provides provider independence.

The implementation must document the exact provider, bucket/area, credentials, retention and encryption configuration before production.

A future move to a second storage provider such as Backblaze B2 remains an approved evolution when independence, scale or retention requirements justify it.

## 4. Media Master Archive

The canonical field-to-archive workflow is:

```text
Field Capture
    ↓
Local Ingest / Verification
    ↓
R2 Private Master
    ↓
Integrity Verification
    ↓
Offline Physical Master Archive
    ↓
Optional Future Independent Cloud Archive
```

An original 360/photo/video/3D master is **not considered safely archived** until at least two independently stored verified copies exist, including the R2 operational copy and the offline physical archive.

The offline archive will initially use an **external HDD**. It is not required to remain connected to the workstation or network.

## 5. Offline HDD Policy

The HDD is an archive layer, not a permanently mounted working disk.

Operational sequence:

```text
Backup / Sync
   ↓
Checksum / Integrity Verification
   ↓
Disconnect HDD
   ↓
Store in controlled physical location
```

The offline archive must undergo **periodic integrity verification** using its manifest/checksums. If corruption or unreadable sectors are detected, the affected archive must be replaced/rebuilt from a known-good copy.

As the media library grows, a second HDD stored in a geographically separate location may be introduced.

The physical HDD is not treated as the only long-term copy. It complements cloud/operational storage.

## 6. Media Versioning ≠ Backup

Immutable/versioned object keys provide history and rollback capability but do not constitute an independent backup.

Preferred structure:

```text
experience/123/master/v001/
experience/123/master/v002/
experience/123/processed/v001/
```

A version may be retained independently from later versions, but deletion/corruption of the underlying storage remains possible. Independent backup/archive remains mandatory for irreplaceable masters.

## 7. Media / Database Consistency

Database media references must carry sufficient metadata to reconstruct publication state and identify the intended asset version, including as applicable:
- asset/object key;
- immutable version identifier;
- ingest timestamp;
- publication state;
- source/master relationship;
- checksum or integrity identifier where practical.

The system does not require distributed transactions between PostgreSQL and R2. Recovery must instead use explicit consistency metadata and post-restore integrity validation.

## 8. Application Rollback

Application releases are tied to Git commits/builds.

```text
Git Commit → Build → Release → Deploy
```

If a release is defective:

```text
Current Release
      ↓
Problem
      ↓
Rollback Application
      ↓
Previous Known-Good Release
```

Application rollback must not automatically roll back the database.

## 9. Database Migration Strategy

Migrations should follow an expand/migrate/contract approach where practical:

```text
Expand → Migrate → Deploy → Contract
```

Destructive schema changes require an explicit recovery strategy. The project must never assume that a previous application binary can safely run against a changed schema without compatibility assessment.

## 10. Recovery Objectives

### RPO

**≤24 hours** initial target for authoritative application data.

For irreplaceable captured masters, the operational target is stronger: no master is considered protected until an independent verified copy exists.

### RTO

**≤4 hours** initial target for application/database service recovery.

This is an operational target, not a guarantee for full restoration of an arbitrarily large media archive. Media recovery time depends on asset volume and recovery method.

## 11. Recovery Configuration Inventory

A non-secret inventory must document all configuration/secrets required to reconstruct production, including:
- secret/configuration name;
- owning service;
- environment;
- provisioning location;
- rotation/revocation procedure;
- recovery owner/role.

Secret values must never be stored in this inventory or in source control.

## 12. GitHub Recovery

Git history is the primary application version history but is not a complete disaster-recovery copy of the repository configuration.

As an operational evolution, maintain a periodic repository/configuration export or mirror where justified, including relevant non-secret workflow/configuration information. Secrets remain managed separately.

## 13. Recovery Procedure

```text
Identify Incident
      ↓
Contain
      ↓
Preserve Evidence where appropriate
      ↓
Choose Recovery Point
      ↓
Recover / Provision Infrastructure
      ↓
Restore Database
      ↓
Restore Critical Media / Verify R2
      ↓
Restore Application Release
      ↓
Provision Secrets Securely
      ↓
Run Integrity & Consistency Checks
      ↓
Validate Explore 360
      ↓
Reopen Service
```

## 14. Restore Validation

A restore test must validate more than successful database commands.

Minimum checks:
- database connectivity;
- record counts / representative records;
- PostGIS queries;
- entity relationships;
- representative Experiences and Routes;
- media references and object availability;
- application health;
- authentication integration where applicable.

Tests should use a temporary recovery environment and must not overwrite production.

## 15. Backup Monitoring

Production backup and export jobs must expose a success/failure signal. A failed required backup/export must create an actionable operational alert or equivalent review mechanism.

The backup schedule and last successful backup must be observable to the operator.

## 16. Recovery Point Integrity

Database exports and offline media archives must have integrity verification. Checksums/manifests must be used for critical masters and independent exports.

For the media archive, a manifest should record at minimum the asset identifier, version, file path/object key, size and checksum.

## 17. 3-2-1 Strategy

The project adopts 3-2-1 as an **evolution target**, not as a claim that every asset has three copies during MVP.

### MVP baseline

```text
Online operational copy
        +
Independent offline physical copy
```

### Evolution

```text
Online operational copy
        +
Offline HDD archive
        +
Independent cloud archive (e.g. B2)
```

A second geographically separate HDD may also be introduced as the archive grows.

## 18. Security of Backups

Backups require:
- encryption at rest where supported;
- restricted access;
- separate credentials/access controls;
- production/staging separation;
- defined retention;
- secure physical storage for offline media;
- no secrets in backup manifests or logs.

## 19. What the MVP Will Not Do

The MVP will not require:
- Kubernetes disaster-recovery clusters;
- multi-region active-active infrastructure;
- complex database replication;
- enterprise DR platforms;
- 24/7 SOC;
- fully duplicated production infrastructure.

These may be considered only when scale or business-criticality justifies them.

## 20. Future Archive — Backblaze B2

Backblaze B2 remains an approved future independent cloud archive option for masters and/or backup exports when the media volume, retention requirement or geographic independence justifies it.

Its adoption is usage-driven rather than a mandatory MVP subscription.

## 21. Cost Principle

No new mandatory backup subscription is required during development/staging beyond the capabilities already selected for the environment.

Production database backup/PITR costs depend on the selected managed PostgreSQL plan. The offline HDD is treated as an operational hardware/archive investment rather than a recurring service subscription.

## Final Decision

**Managed PostgreSQL backup/PITR + daily independent database export + R2 protected masters + offline external HDD master archive + versioned application/media assets + tested recovery procedures** is the approved R5.5 target architecture.

Backblaze B2 remains the preferred future independent cloud archive option when justified by scale, retention or geographic separation.
